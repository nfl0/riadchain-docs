---
title: Maintain the FILE archive
description: Verify content-addressed FILE bytes, recover missing objects and clean up canonically retired data.
---

Native FILE storage is part of a Riadchain node. A FILE transaction commits a UnixFS CID, size and metadata. The node stores verified object bytes separately from signed `history.log` under `objects/`. A CID does not imply that another service has the content.

## From upload to confirmation

The wallet constructs and signs a FILE transaction for an exact CID and size, stages its bytes through authenticated `NetworkService.StageFile` and submits the original transaction. The SDK methods `prepareFile()` and `stageFile()` support this bounded workflow. Staging chunks are at most 1 MiB. The default new-network ceiling is 300 MiB per file. Compare the genesis limits and fees before a large upload.

The producer verifies length and CID before committing bytes and applies the network's signed peer-acknowledgement policy. A standalone network can confirm with local verification alone. On a network that requires one peer copy, keep that peer reachable and ready. A staged upload has yet to enter the signed history.

After a lost response, inspect the original transaction and resume staging with that same ID if appropriate. Look for a matching successful receipt before reporting confirmation.

## Check local completeness

Use authenticated status to check whether the archive verified. For one object, retrieve it with `NetworkService.ReadFile` or `NetworkClient.readFile()` and verify its CID and length. A receipt proves the reference was confirmed. A successful read with matching bytes establishes availability on the node that served it.

To audit signed history and required local bytes, stop the daemon and run:

```sh
riadchain-cli --config /etc/riadchain/node.toml inspect
```

## Recover missing content

Authenticated peers can supply missing FILE bytes. A node may have verified the signed block history while some objects still need recovery. Check archive completeness separately from block height. Signed history cannot recreate missing bytes. Keep [verified backups](/node/backup-recovery/) in independent failure domains.

## Retire a file

The upload owner can sign a retirement of that original FILE transaction. The retirement and the original reference both remain in signed history. If uploads share a CID, the bytes remain required until every active reference is retired.

After confirming the retirement, the operator can stop the node and explicitly reclaim eligible local bytes:

```sh
riadchain-cli --config /etc/riadchain/node.toml prune-retired-files
```

Only locally stored bytes covered by confirmed retirement are eligible. Existing backups and copies on other machines may still contain them. Coordinate cleanup separately on each node if desired.

## Capacity and privacy

FILE storage charges a one-time fee. Plan for the ongoing growth of signed history, retained objects and independent backups. Treat file bytes and metadata as readable to authorized parties with network access. Encrypt sensitive bytes before upload and manage decryption keys separately.

Read [protocol storage](/protocol/storage/) for the distinction between signed references and local bytes.
