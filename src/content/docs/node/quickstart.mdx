---
title: Create a network
description: Create a private Riadchain network and start its first validator with signed genesis and its own protected machine credentials.
---

Use this guide to **create a new private network**. To start with Android Manager and the separate wallet, follow [Create your network](/appliances/first-network/) before preparing any genesis or node data manually. To add an existing network's reserved machine, follow [peer enrollment](/node/operations/#enroll-a-follower) with its original credentials and genesis pin.

## Prepare the machine

Use the [Debian installation](/node/direct-install/) or [Proxmox](/node/proxmox/) guide for a packaged deployment. If you have the implementation checkout, build the standard native binaries with its pinned Rust toolchain and lockfile:

```sh
cargo build --locked --release -p riadchain-node --bin riadchaind --bin riadchain-cli
```

The examples assume both binaries are on your `PATH`. Use a trusted workstation with the same CLI for initial key generation. Prepare two new directories:

```sh
umask 077
riadchain-cli init node-a reserved-node-b --standalone
```

This creates one signed ML-DSA-65 genesis with distinct machine and signing credentials. The first node starts alone. The second directory is reserved for its own machine later. By default, the first two signing addresses receive 10,000 RDC each, matching the minimum confirmed balance for production. The default succession timeout is one hour. Keep the signing funds available and use a separate spending account for routine transfers or fees.

The CLI prints the full 96-character genesis hash and enrolled public addresses. Record and compare the hash over a trusted channel. Copy each directory's contents, including hidden files, only to its designated machine. For the packaged node, provision those contents at the root of the dedicated data mount. Retain separate, protected copies of each machine's `node.json`, `peer.seed` and `producer.seed`. Keep the reserved second directory private while its machine is offline.

To fund additional user accounts at genesis, pass one `--wallet` public registration JSON file per account. `--wallet-funding` and `--min-stake` accept base units. One RDC is 100,000,000 base units. Use the matching CLI's `init --help` before preparing custom allocations.

## Start the validator

Create `node.toml` on the first machine. Fill in its data directory and the full verified hash. Packaged installations also need [dedicated storage settings](/node/configuration/#dedicated-packaged-storage).

```toml
data_dir = "node-a"

[network]
genesis = "replace-with-the-full-genesis-pin"
peers = []
```

```sh
riadchain-cli --config ./node.toml config check
riadchaind --config ./node.toml
```

Use the packaged service for normal unattended operation. For wallet or authenticated status requests, configure [client RPC access](/node/configuration/#authenticate-client-and-peer-traffic). Then run:

```sh
riadchain-cli --config ./node.toml status
riadchain-cli --config ./node.toml healthcheck
```

Check readiness and advancing blocks. Keep the same signed identity and data directory when restarting. The CLI's config check verifies local inputs and their binding but does not establish live readiness.

## Add redundancy before relying on the chain

A separate machine verifies signed history and can retain another copy of your FILE archive. An enrolled machine with zero RDC can sync and serve data. An eligible successor also needs the minimum confirmed spendable balance and successful authenticated startup synchronization. See [peer enrollment](/node/operations/#enroll-a-follower) and [succession](/protocol/succession/).

Standalone native setup verifies local FILE bytes and does not require a peer acknowledgement. Use the signed network's actual parameter when assessing whether an upload can confirm. Before storing important data, create a [verified backup](/node/backup-recovery/) on separate storage.
