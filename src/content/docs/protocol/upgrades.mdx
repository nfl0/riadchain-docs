---
title: Protocol upgrades
description: Learn how networks coordinate new consensus rules at an agreed height and preserve verifiable history.
---

A network upgrade (NU) changes the rules nodes use to validate and execute
blocks. Operators agree on the rules and activation height outside the chain.
Each node needs software with the same rules and the same activation plan.
An application administrator has authority over its
[contract](/build/abi-and-guards/), separate from the network's rules.

## Independent protocol IDs

A signed block commits a numeric protocol ID. It identifies consensus and
execution rules. A node package version identifies software. Multiple package
revisions can implement the same rules.

The current private release starts with protocol ID **3** from its
[signed genesis](/protocol/genesis/). Storage scans, typed hashing, authenticated
chain context and the other initial VM capabilities are available on a fresh
network. Installing a newer package that implements these rules preserves the
original chain. Use the installed CLI to check its supported rule IDs:

```sh
riadchain-cli protocol capabilities
```

The current private release does not have a configurable height-based scheduler.
A future upgrade requires a release that implements both the proposed rules and the
agreed activation mechanism. Manager currently installs signed node software
per machine. Follow the [appliance update workflow](/appliances/updates-and-help/)
and the network's own maintenance plan.

## Execution at an activation

In a release with scheduled activation, the new rules apply beginning with the
agreed block. Older blocks replay with their original rule IDs. A node lacking
the scheduled rules must stop at that boundary. Otherwise, participants could
accept different results for the same signed history.

Nested calls and due scheduled calls share the enclosing block's execution
rules. Current-state views use the tip's rules. Admission and simulation for
the next block can begin using an upcoming ruleset before that first block is
produced.

## Coordinate a supported upgrade

1. Read the release's activation instructions. Confirm support on producers,
   following nodes and recovery machines.
2. Verify a [backup of signed history and FILE data](/node/backup-recovery/)
   and agree on the same future activation height.
3. Install the supporting release and apply its activation procedure on each
   machine. Compare the agreed rule ID and height before the activation block.
4. Verify that participants accept the same signed activation block and
   continue producing and synchronizing normally.

Retain the activation record with your recovery material. A historical block
keeps the rules committed by its signature. Do not edit its historic activation
to resolve a failed installation or a disagreement between operators.
