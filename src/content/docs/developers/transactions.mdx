The examples use the [revision 59 workspace SDK](/developers/sdk/#connect-to-revision-59).
Keep the transaction's chain, signing account, review identity and original ID
bound through preparation, approval, signing, submission and recovery.

## Prepare and review

This function prepares an unsigned transfer with `riad1…` owner and recipient
addresses. Express amounts and fees in base units.

```ts
import type { NetworkClient } from '@riadchain/sdk/network';

export function prepareTransfer(
  client: NetworkClient,
  owner: string,
  recipient: string,
  amount: bigint,
  maxFee: bigint,
) {
  return client.prepareTransfer({ owner, recipient, amount, maxFee });
}
```

Inspect the draft's `intent`, fee, change, expiry height, chain and original ID.
Bind approval to `approvalId`; use `encodeNetworkDraft` and
`decodeNetworkDraft` if you need to store the exact draft across that step.
On approval, `client.sign(draft, signer)` validates the draft, the ML-DSA-65
signer and the account's current key epoch. Recheck the active wallet session
and any application assumptions that could have changed since review.

Keep secrets in the wallet or a protected non-browser service. If a wallet
method can broadcast itself, save the original ID and reviewed intent before
invoking it. Native simulation requires a signed original and reports execution
against the selected tip; obtain approval before signing a simulated intent.

## Journal before broadcast

This helper accepts an already reviewed and signed transaction. The application
must implement durable storage scoped to its chain and account.

```ts
import {
  encodeNetworkSubmission,
  type NetworkClient,
  type NetworkSignedTransaction,
} from '@riadchain/sdk/network';

export async function submitReviewed(
  client: NetworkClient,
  signed: NetworkSignedTransaction,
  save: (id: string, bytes: Uint8Array) => Promise<void>,
) {
  await save(signed.id, encodeNetworkSubmission(signed));
  try {
    return await client.submit(signed);
  } catch {
    return { id: signed.id, status: 'unknown' as const };
  }
}
```

A returned acknowledgement identifies the original attempt. Use
`getTransaction(id)` or `waitForTransaction(id, { timeoutMs: 120_000 })` to
reconcile it. Concurrent account writes should share a submission lock and keep
inputs reserved for an unresolved original.

## Interpret outcomes precisely

| Observation | Meaning |
| --- | --- |
| `queued` | The node has retained the original for processing. |
| `confirmed`, `success: true` | The matching signed transaction executed successfully. |
| `confirmed`, `success: false` | The matching transaction was included and execution failed. Inspect the [execution page](/developers/rpc/#account-history-and-block-execution). |
| `rejected` | The node records rejection of that original. |
| `unknown`, timeout or lost response | Keep the original and reconcile it again on the same chain. |

When retrying an identical submission, recover the signed artifact with
`decodeNetworkSubmission(savedBytes)`. A missing observation never proves that
another endpoint did not receive it. Review a new transaction only after the
original is settled or proven incapable of execution, including its expiry and
input status. Keep the same signed artifact and bytes for
[FILE staging](/developers/files/#stage-the-signed-original-before-submitting).
